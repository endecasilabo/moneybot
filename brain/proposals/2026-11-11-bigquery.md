## Problema

Cloud SQL es una instancia Postgres siempre encendida para unas pocas escrituras al día. Cuesta
dinero aunque no se use, y obliga a mantener un proxy, una IP pública (para el paso `schema` del
CI), una contraseña en Secret Manager y un socket montado en cada job. Además, el uso que viene
(barras horarias, métricas, análisis y backtests sobre lo guardado) es analítico, que es donde
BigQuery encaja mejor.

## Alternativas consideradas

1. **Seguir en Cloud SQL.** Transaccional, con `UPDATE` y claves únicas reales. Pero tiene coste
   fijo, más piezas de infra y es peor para análisis.
2. **BigQuery para todo** — **elegida**. Sin servidor, entra en el free tier a este volumen y es
   nativo para análisis. Exige diseñar las escrituras como "solo añadir" (ver abajo).
3. **Híbrido: Cloud SQL para coordinar (intents, runs) y BigQuery para análisis.** Lo mejor de
   cada uno, pero mantiene todo el coste y la complejidad de Cloud SQL más un pipeline de copia.
   Excesivo para un PoC.

## Qué cambia al pasar a BigQuery (y cómo se resuelve)

- **No hay PK ni UNIQUE que se apliquen.** La idempotencia de las órdenes la garantiza Alpaca
  (rechaza un `client_order_id` repetido, caso ya tratado), y las tablas son para auditar.
- **No hay autoincrementales.** Los `run_id`, `signal_id`, etc. pasan a ser UUID generados en
  Python.
- **Los `UPDATE` son lentos y chocan entre sí.** Todas las tablas pasan a ser **solo añadir**: un
  cambio de estado es una fila nueva con su `event_ts`, y las vistas `*_latest` dan el estado
  actual. Como nunca se actualiza, se puede escribir por streaming (`insert_rows_json`) sin la
  restricción de DML sobre filas recién insertadas.
- **`MERGE` solo en `bars`** (rama siguiente, job `ingest`). Corre una vez por hora, sin
  concurrencia.

## Decisiones (2026-11-11)

- Dataset `moneybot` en **`US`** (multi-región). `moneybot_dev` en `US` para pruebas locales. El
  dataset `src` (prueba previa) no se toca.
- Se empieza de cero. No se migran datos de Cloud SQL, porque con `trading_enabled: false` no hay
  órdenes reales.
- Cloud SQL se retira en un PR posterior, cuando BigQuery esté verificado en producción.
- `bars` con `adjustment=split`, más re-ingesta del histórico diario. Se guarda la columna
  `adjustment` para poder cambiar.
- Esta rama migra los jobs actuales (`trade`, `snapshot`) y crea ya el modelo completo. Los 4 jobs
  van en la rama siguiente.

## Modelo de datos

Convenciones: `TIMESTAMP` en UTC, `session_date DATE` en hora de Nueva York, `NUMERIC` para
precios, cantidades y dinero (salvo `bars`, que usa `FLOAT64`, como Alpaca), claves UUID o
naturales.

| Tabla | Qué guarda | Partición / cluster | Escrita por |
|---|---|---|---|
| `runs` | Eventos de cada ejecución (`running` → `ok`/`skipped`/`error`) | `DATE(event_ts)` / `job` | todos (`guarded`) |
| `signals` | Qué vio y qué decidió `decide()`, **con los parámetros de la estrategia** (JSON) | `session_date` / `symbol` | `trade` (luego `trigger`) |
| `orders` | Eventos de orden: envío, error, duplicado (más adelante, fills) | `DATE(event_ts)` / `symbol` | `trade` (luego `execute`) |
| `account_snapshots` | Equity, cash, buying power y órdenes abiertas (JSON) | `DATE(ts)` | `snapshot` |
| `position_snapshots` | Una fila por posición | `DATE(ts)` / `symbol` | `snapshot` |
| `bars` | OHLCV por `symbol`, `timeframe` (`1Hour`/`1Day`) y `ts` | `DATE(ts)` / `symbol, timeframe` | `ingest` (rama siguiente) |
| `assets` | Dimensión de instrumentos (clave `symbol`) | — | manual o `GET /v2/assets` (más adelante) |
| `order_intents` | Eventos de intent (`pending` → `sent`/`skipped`/`error`/`expired`) | `session_date` / `symbol` | `trigger` / `execute` (rama siguiente) |

Vistas: `runs_latest`, `orders_latest` y `order_intents_latest` (último evento por clave).

Queda fuera del PoC: `metrics` (formato largo `ts, symbol, metric, value`, se crea con la primera
métrica real), carteras y estrategias como entidades, y un log sink a BigQuery (Cloud Logging ya
guarda el stdout).

## Resultado de la implementación (2026-11-11)

- `dbt build` contra `moneybot_dev`: 8 tablas + 3 vistas + 11 tests OK, e idempotente (segunda
  pasada sin cambios). Partición y clustering verificados con `bq ls`.
- Ciclo real contra `moneybot_dev`: `start_run` → `insert_signal` (con `params` JSON) →
  `record_order` → `sent_order` (pasa de `False` a `True` al instante, el streaming se puede
  consultar) → snapshots → `finish_run`. Las vistas `*_latest` devuelven el último estado.
- Tests: 61 OK (3 nuevos en `tests/test_db.py`).
- Terraform: `fmt` y `validate` OK (Terraform 1.9.8, en local, sin backend). No se ha aplicado.

### Orden de despliegue tras el merge

1. **Deploy** (automático en `main`): `infra` crea el dataset y el IAM, y `build` publica la imagen
   nueva. A partir de aquí, **los jobs fallan con `missing env BQ_DATASET`** hasta el paso 3. Es un
   fallo seguro: abortan antes de llamar a Alpaca.
2. **Infra → `schema`**: dbt crea las tablas y vistas en `moneybot`.
3. **Infra → `jobs`**: los jobs reciben `BQ_DATASET` y dejan de montar Cloud SQL.
4. Lanzar `moneybot-snapshot` a mano y comprobar las filas en `moneybot.runs_latest`.
